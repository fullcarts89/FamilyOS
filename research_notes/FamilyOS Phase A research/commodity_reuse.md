## 1. Open-source household apps: learn from, embed, or base on? License traps? Reuse recurrence logic?

### Takeaway
None of these projects is a suitable base for a multi-tenant, commercial, agent-capable FamilyOS. The best chore/recurrence products (Donetick, HomeBox, Mealie) are AGPL-3.0. Tandoor is AGPL plus a Commons Clause that forbids selling. Homechart is not open source, and Cal.com's production code went private in April 2026. Grocy (MIT) and Home Assistant (Apache-2.0) are permissive but single-household, self-hosted designs. Use these apps as UX and behaviour references. Do not copy AGPL code, and write FamilyOS's own small recurrence engine.

### Cited Findings
- **Donetick** (chores): license AGPL-3.0; latest release v0.1.86 on 2026-11-03; last push 2026-11-06; about 2.7k stars. — [GH API: donetick/donetick](https://github.com/donetick/donetick/releases) (acc. 2026-11-07)
- Donetick's README lists daily/weekly/monthly/yearly/specific-days schedules, "adaptive scheduling" learned from past completions, a choice between **due-date-based and completion-date-based recurrence**, assignee rotation (fewest completions, random, round-robin), subtasks that reset on completion, and completion windows (a task can only be completed within X hours before it is due). It states the project "is licensed under the **AGPLv3**". The scheduler code is in `internal/chore/scheduler.go`, with tests in `scheduler_adaptive_test.go` and `scheduler_test.go`. — [Donetick README](https://github.com/donetick/donetick/blob/main/README.md) (acc. 2026-11-07)

A secondary report describing the main product as "proprietary" conflicts in framing. — [letsdatascience.com](https://letsdatascience.com/news/calcom-closes-commercial-codebase-sparks-security-debate-d5e0d3fd) (acc. 2026-11-07)

### Inferences
- **AGPL trap:** AGPL-3.0 §13 requires offering source to network users of a *modified* version. Embedding or forking Donetick, HomeBox or Mealie into a hosted FamilyOS would therefore force FamilyOS to publish its server source. Reading these projects for behaviour and test cases is fine. Copying code, including Donetick's `scheduler.go`, is not, unless FamilyOS accepts AGPL for that component.
- **Tandoor is not usable commercially** because the Commons Clause forbids selling, including hosting.
- **Homechart is not reusable code.** Treat it as a competitor and UX reference. It is the closest product analogue: a paid household "mission control" at $4.99/month.
- **Grocy (MIT)** could legally be reused with attribution. However, it is PHP, single-household, single-database and has no tenancy, so it is a poor base. Its chore semantics are worth studying.
- **Cal.diy (MIT)** is legal to reuse, but its README discourages production use and the team and workflow features are removed. Calendar scheduling for vendor appointments is better handled with a small booking-slot model, or later by integrating a hosted scheduler, than by embedding Cal.diy.
- **Recurrence:** build FamilyOS's own engine (see Section 2), and use Donetick's feature list as the spec checklist: due-date vs completion-based recurrence, rotation, completion windows, subtasks that reset on completion.

### Gaps
- I did not verify Grocy's chore "period types" (for example, whether a dynamic/after-completion mode exists) from primary docs.
- I did not check Home Assistant's 2026 release notes for any new chores or household features.
- Mealie and Tandoor hosted pricing were not checked.

## 2. Recurrence and time: libraries, RFC 5545 semantics, Temporal, DST, skip-one, after-completion

### Takeaway
Model FamilyOS recurrence as (a) a calendar rule stored as RFC 5545 RRULE text plus an IANA TZID and local wall-clock DTSTART, with skips stored as exception rows (EXDATE semantics), and (b) a separate "interval after completion" mode that is not an RRULE. RFC 5545 has no completion-anchored recurrence; VTODO only has a COMPLETED timestamp. python-dateutil had a fresh 4.0.0 release on 2026-11-01. rrule.js has not had an npm release since 2023 and its handling of floating UTC dates is error-prone. Temporal is finished at TC39 but Safari and React Native (Hermes) support is unverified, so use a polyfill or keep date math on the server.

### Cited Findings
- RFC 5545 §3.3.10: when a rule generates an invalid date (for example Feb 30) or a nonexistent local time, the instances "MUST be ignored and MUST NOT be counted as part of the recurrence set". The same section also says that when a computed local start time does not exist or occurs twice, it is interpreted as in §3.3.5. — [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545.txt) (acc. 2026-11-07)
- RFC 5545 §3.3.5: a nonexistent local time is "interpreted using the UTC offset before the gap in local times". The RFC's example is `TZID=America/New_York:20070311T023000`, which becomes 3:30 AM EDT. An ambiguous (repeated) local time refers to its first occurrence. — [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545.txt) (acc. 2026-11-07)
- RFC 5545: the recurrence set is built from RRULE and RDATE values minus EXDATE values, and EXDATE takes precedence. If EXDATE excludes DTSTART, the original DTSTART must still be kept because RECURRENCE-ID depends on it. RANGE=THISANDFUTURE on RECURRENCE-ID applies an override to an instance and all later ones. — [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545.txt) (acc. 2026-11-07)
- RFC 5545 COMPLETED (on VTODO) is a UTC DATE-TIME recording when a to-do "was actually completed". Nothing in the RRULE grammar anchors recurrence to completion. COUNT always counts DTSTART as the first occurrence. — [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545.txt) (acc. 2026-11-07)
- **rrule.js**: npm `rrule` 2.8.1, published 2023-11-10, BSD-3-Clause; latest GitHub release v2.7.1 (2022-07-14); last repo push 2024-06-27. — [npm rrule](https://www.npmjs.com/package/rrule); [GH jkbrzt/rrule](https://github.com/jkbrzt/rrule) (acc. 2026-11-07). The README says it uses "floating" times or UTC by default, so returned UTC-labelled dates must be read as local times. It supports `tzid` through the Intl API and offers RRuleSet with exdate. — [rrule README](https://github.com/jkbrzt/rrule/blob/master/README.md) (acc. 2026-11-07)
- **python-dateutil** 4.0.0 was released 2026-11-01; PyPI lists BSD-3-Clause. It requires Python ≥3.11, drops `six`, and fixes a hang when iterating a cached `rrule`/`rruleset` after another iterator completed the cache. — [GH dateutil 4.0.0 release](https://github.com/dateutil/dateutil/releases); [PyPI python-dateutil](https://pypi.org/project/python-dateutil/) (acc. 2026-11-07)
- **rschedule**: npm `@rschedule/core` 1.5.0, published 2023-02-03, license Unlicense. The GitHub path `rschedule/rschedule` returned 404. — [npm @rschedule/core](https://www.npmjs.com/package/@rschedule/core) (acc. 2026-11-07)
- **Temporal**: TC39's finished-proposals list includes Temporal with expected publication year **2027**. — [tc39/proposals finished-proposals.md](https://github.com/tc39/proposals/blob/main/finished-proposals.md) (acc. 2026-11-07). Secondary reports say it reached Stage 4 in March 2026 and ships unflagged in Chrome/Edge 144, Firefox 139 and Node.js 26. Reports of Safari support conflict. — [InfoQ](https://www.infoq.com/news/2026/02/chrome-temporal-date-api); [lilting.ch](https://lilting.ch/en/articles/nodejs-26-current-temporal-undici) (acc. 2026-11-07). One secondary source says "ES2026", which conflicts with the primary list's 2027 publication year.
- Polyfills: `temporal-polyfill` (fullcalendar) 1.0.8, published 2026-11-04, MIT; `@js-temporal/polyfill` 0.5.1, published 2025-03-31, ISC. — [npm temporal-polyfill](https://www.npmjs.com/package/temporal-polyfill); [npm @js-temporal/polyfill](https://www.npmjs.com/package/@js-temporal/polyfill) (acc. 2026-11-07)
- Donetick offers both due-date-based and completion-date-based recurrence, which confirms that real chore apps need both modes. — [Donetick README](https://github.com/donetick/donetick) (acc. 2026-11-07)

### Inferences
- **RFC tension:** §3.3.10 says to ignore nonexistent-time instances, yet it also refers to §3.3.5, which shifts them. Libraries differ on this. FamilyOS should pick one documented policy and pin it with tests. For chores, shifting forward (for example, 2:30 AM on spring-forward becomes 3:30 AM) is friendlier than silently dropping a chore. Most household chores are date-only (all-day, `VALUE=DATE`), which avoids DST issues entirely. Use timed rules only for reminders.
- **Data model:** `recurrence_rule (rrule_text, tzid, dtstart_local, mode ENUM(calendar, after_completion), interval, unit)` plus materialized `occurrence` rows (`due_local_date`, `state`, `override_owner`, `skipped_at`). "Skip one" means marking that occurrence skipped (EXDATE semantics). The rule is never edited. "This and future" edits split the series (new rule from date X), which mirrors THISANDFUTURE.
- **After completion:** `next_due = local_date(completed_at, household_tz) + interval`. This is not an RRULE. Store it as its own mode. Decide whether a missed occurrence blocks the next one: the PRD says missed tasks go to Needs Attention.
- **Library choice:** with a Python backend, use python-dateutil 4.x `rrulestr` + `zoneinfo`. With a TypeScript backend, rrule.js is serviceable with `tzid`, but its floating-UTC convention needs a wrapper and the project shows little maintenance. Alternatively implement the subset FamilyOS needs (DAILY/WEEKLY/MONTHLY/YEARLY with INTERVAL, BYDAY, BYMONTHDAY, BYSETPOS=-1) on Temporal through `temporal-polyfill`. Do recurrence generation on the server so mobile JS engine support for Temporal does not matter.

### Gaps
- Temporal support status for Safari/iOS and Hermes (React Native) could not be confirmed from primary sources. The search budget was exhausted.
- rrule.js DST behaviour around gaps was not tested. It needs a FamilyOS test suite (America/New_York 2026-03-08 and 2026-11-01).

## 3. Auth and tenancy: Supabase vs alternatives; authorization engines; household invites

### Takeaway
Supabase Pro ($25/month including $10 compute credit) bundles Postgres, Auth (100k MAU), Storage (100 GB), Realtime and Queues. At FamilyOS scale its cost is effectively flat. RLS is a good tenant-isolation backstop if every policy is indexed and wrapped as Supabase recommends. The main failure modes are secret/service keys bypassing RLS, views bypassing RLS, RLS not applied to DELETE events in Realtime, and missing policies, as in the Lovable CVE. Supabase Auth has no household/org primitive, so FamilyOS builds `household`, `membership` and `invite` tables itself, or uses Better Auth's organization plugin. Clerk becomes expensive because each household is a billable organization: about $900/month at 1,000 households. External authorization engines are overkill. Use plain RLS plus a role table, with authorization checks in deterministic code.

### Inferences
- **Recommendation: Supabase (Pro) as the managed Postgres + Auth + Storage + Realtime bundle**, with all writes through a FamilyOS API server that uses a user-scoped JWT, so RLS still applies. The service key should be reserved for narrowly scoped workers that filter explicitly by household ID. Neon, Railway or Render plus own code is a reasonable alternative if FamilyOS wants portability. In that case FamilyOS must add its own object storage, auth (Better Auth) and realtime, which is more engineering for little saving at under 1,000 households.
- **Household = tenant.** Tables: `household`, `membership(household_id, user_id, role)`, `invite(token_hash, household_id, role, expires_at, accepted_by)`. RLS policy shape: `household_id IN (select household_ids_for_user())`, using a `security definer` helper wrapped in `select`, with an index on `household_id`. Add pgTAP or integration tests that try cross-household reads and writes, as required in the brief's security section.
- **Invite flow:** single-use, hashed token with 48h expiry (Better Auth's default) delivered by email deep link. Require the invitee's email to match, or confirm explicitly. Show the role being granted. The inviter must be an admin.
- **Clerk cost trap:** a household with two adults is an MRO. At 1,000 households that is 900 billable MROs × $1 ≈ $900/month on top of the plan. Clerk is cheap only while there are 100 or fewer households.
- **Permit's free tier caps tenants at 20.** If household = tenant it is useless for FamilyOS.
- **AuthZ engines (OpenFGA, Cerbos) are overkill** for 4–5 fixed household roles. They also add a second source of truth alongside RLS. Revisit only if per-object sharing across households (for example with a nanny or co-parent) becomes complex. Plain RLS + role table + deterministic approval service matches the PRD's "keep LLM out of authorization."

### Gaps
- Render's paid instance and Postgres prices were not extractable (JS-rendered page).
- Supabase Queues GA status and pricing (beyond underlying compute) are not stated on the pages read.
- Neon storage figures: the extracted table showed "1 GB/project, 20 GB total" on Free. I did not re-verify this.

## 4. Client: Expo/React Native vs PWA vs SwiftUI; iOS web push in 2026; EAS pricing; share sheet and photo capture

### Takeaway
Use Expo (React Native) for one-handed capture, share-sheet intake and reliable APNs/FCM push. Expo Push is free and there is one codebase for iOS and Android. iOS PWA push still requires the user to add the site to the Home Screen and grant permission from a tap, which hurts reliability for a capture-first app. EAS Free or Starter ($19/month) is enough at this stage. SwiftUI-native is the highest-quality but iOS-only route.

### Cited Findings
- **Expo**: `expo` 58.0.23 published 2026-11-03, MIT; repo pushed 2026-11-07. — [npm expo](https://www.npmjs.com/package/expo); [GH expo/expo](https://github.com/expo/expo) (acc. 2026-11-07)

## 5. Email channel: inbound parsing and outbound relay

### Takeaway
Use **Postmark Pro** ($16.50/month for 10k emails, $1.30/1k overage, inbound included, plus-address `MailboxHash` for per-project reply routing, 45-day retention extendable to 365) or **Resend Pro** ($20/month for 50k, inbound counts against quota, catch-all receiving, 30-day retention). Amazon SES is roughly 10–15× cheaper but means building inbound plumbing (S3, SNS, Lambda) and leaving the sandbox. Cloudflare Email Routing gives free inbound to Workers, and its sending product is still beta. Every provider's acceptable-use policy forbids "unsolicited" or "cold" email. ### Inferences
- **Per-project reply addresses:** send from `"The Lee household via FamilyOS" <projects@mail.familyos.app>` with `Reply-To: p+<opaque_project_token>@reply.familyos.app`. Postmark exposes the token as `MailboxHash`; Resend and Cloudflare expose it as the To address with a catch-all. Also store the outbound `Message-ID` and match on `In-Reply-To`/`References` as a second key, because vendors sometimes reply from another address or strip plus-tags. The token must be unguessable and unrelated to the household ID, and inbound mail must be checked against the project's expected vendor addresses before it is treated as trusted. Inbound email is a prompt-injection surface.
- **DKIM/DMARC:** use a dedicated sending subdomain with aligned DKIM, SPF via the provider's return-path, and DMARC starting at `p=none` and moving to quarantine. FamilyOS is far below Gmail's bulk threshold, but alignment still helps deliverability to small-business inboxes (often Gmail or Google Workspace).
- **"Cold-ish" single messages to vendors:** Resend's AUP expressly lists cold outreach as prohibited, and Postmark's terms require permission-based lists. A user-approved, one-to-one inquiry to a business's published contact address on the household's behalf is arguably a requested service inquiry, not a list send, but no provider page states that. Recommendation: (1) ask the chosen provider in writing before alpha; (2) keep volumes tiny, one message per vendor per project and no automated follow-up sequences; (3) consider sending from the user's own mailbox via Gmail or Microsoft OAuth as an alternative channel (another researcher covers legal aspects).
- **Retention:** Postmark (45 days by default, up to 365) or Resend (30 days) are not the system of record. FamilyOS should persist raw MIME plus parsed JSON in its own storage on receipt.
- **Pick:** Postmark Pro for best inbound ergonomics and a long-standing transactional reputation. Resend for cheaper volume. SES only if building inbound plumbing is acceptable.

## 9. Document handling: virus scanning, PDF/photo extraction, EXIF stripping

### Takeaway
Use a frontier-model vision call with structured outputs for receipts, invoices and photos of appliance labels. Anthropic, OpenAI and Gemini all support image input, and cost per document is fractions of a cent on small models. Keep Docling (MIT) as an optional local PDF-to-text pre-step. ## 10. Search and memory: Postgres full-text + pgvector vs mem0, Zep, Letta

### Takeaway
Household memory with citations belongs in FamilyOS's own Postgres: canonical records (assets, vendors, documents, decisions) plus `tsvector` full-text search and pgvector embeddings keyed to record IDs, all under the same RLS. Agent-memory products (mem0, Zep, Letta) add a second, LLM-mutated store outside tenant RLS. Their "memories" are model-written summaries, which works against the PRD's requirements to cite the underlying record, answer "unknown" instead of guessing, and support delete and export.

### Cited Findings
- **pgvector**: latest tag v0.8.7 on the repo; Python client `pgvector` 0.5.1 (2026-10-09, MIT). — [GH pgvector/pgvector](https://github.com/pgvector/pgvector); [PyPI pgvector](https://pypi.org/project/pgvector/) (acc. 2026-11-07). Supabase recommends pgvector over Vector Buckets for user-facing, quick-response features. — [Supabase Vector Buckets](https://supabase.com/docs/guides/storage/vector/introduction) (acc. 2026-11-07)
- **mem0**: Apache-2.0; `mem0ai` 2.2.1 (2026-09-25). The Free plan has unlimited end users; for 30 days you get 10k adds and 1k retrievals per month, then 50k adds and 10k retrievals per month with your own LLM key. Graph memory, user profiles, SSO, audit logs and on-prem are on the Custom plan. — [GH mem0ai/mem0](https://github.com/mem0ai/mem0); [mem0.ai/pricing](https://mem0.ai/pricing) (acc. 2026-11-07)
- **Zep**: Flex $125/month (50k credits); Flex Plus $375/month (200k credits); Enterprise custom (SOC 2 Type II, HIPAA BAA, BYOC). One credit covers 350 bytes of an ingested "episode"; retrieval and storage are unmetered. API log retention is 1 day on Flex. — [getzep.com/pricing](https://www.getzep.com/pricing) (acc. 2026-11-07). Graphiti (Zep's graph engine) is Apache-2.0, v0.31.2 (2026-10-20). — [GH getzep/graphiti](https://github.com/getzep/graphiti) (acc. 2026-11-07)
- **Letta**: Apache-2.0; GitHub latest release 0.16.8 (2026-05-14), while PyPI `letta` is 0.34.12 (2026-10-12), which suggests different version streams. — [GH letta-ai/letta](https://github.com/letta-ai/letta); [PyPI letta](https://pypi.org/project/letta/) (acc. 2026-11-07). Pricing now redirects to a Letta Code page: Free (3 agents), Pro $20/month, Teams Pro $20/seat. — [docs.letta.com/letta-code/pricing](https://docs.letta.com/letta-code/pricing) (acc. 2026-11-07)

### Inferences
- **Reasons not to use an agent-memory product for household memory:** (1) Tenant isolation: memories live outside Postgres RLS, so a second authorization model is needed for every read. (2) Citations: these products store LLM-extracted facts, so tracing an answer to the specific document or record takes extra bookkeeping. The PRD requires "answers reference underlying record". (3) Deletion and export: deleting a document must also delete derived memories, which is harder across systems. (4) Cost and vendor exposure: Zep starts at $125/month; mem0's useful features are on Custom.
- **Design:** `search_index(record_type, record_id, household_id, chunk_text, tsv tsvector, embedding vector(…))` with GIN and HNSW indexes. Hybrid rank (BM25-like `ts_rank` plus cosine). The answer generator may only cite returned `record_id`s, and it returns "unknown" if retrieval comes back empty. A short-lived "agent scratchpad" for a running workflow belongs in the workflow engine's state (another researcher's scope), not in a memory product.

### Gaps
- pgvector's exact license (GitHub reports NOASSERTION) was not read from the LICENSE file. The project is widely understood to use the PostgreSQL License, but I did not verify this.
